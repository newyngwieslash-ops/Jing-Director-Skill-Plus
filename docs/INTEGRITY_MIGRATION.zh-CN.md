# 4.2 内容保真与审核证据迁移

## 不变的边界

本包仍是离线导演规划与编译工具，不提交模型、不上传参考、不认证用户身份。原镜号、顺序、时长和源文本不得为了通过校验而改写。旧样例没有真实批准、图像与生成记录；不得自动补齐这些事实。

## 来源基线与对白

旧合同可继续 plan 与显式 --draft 处理，缺少完整来源证据时会给出警告；非草稿 compile 要求 --source 指向独立保存的来源快照。production 也需要独立基线。合同的来源摘要和 source_shots 必须与该快照一致。

每条 source shot 新增 dialogue_baseline：status 为 reviewed，reviewed_by 与 evidence 记录实际复核者和依据，lines 保存对白清单。每条 line 含稳定 id、text 与 sound_span=[start,end]，按原 sound 字段的 Unicode 字符偏移精确定位，结束位置不包含在内。对白必须按源顺序、不重叠地映射原文。已核对确无对白的镜头明确 lines=[]；不能由程序把所有声音描述强行当台词，也不能根据空 dialogue 自动推断无对白。

合同 dialogue 每项通过 source_dialogue_id 引用源清单；每条源对白在关联镜头中必须恰好出现一次，保留文字和顺序。原镜拆分不能靠重复或遗漏台词通过。初版不支持自动将一句台词切分为多条映射，遇到此类需求应先形成明确来源方案，不能擅自删减。

重要：基线相等证明当前合同与保留的快照一致，不证明该快照是真实原件，也不验证 reviewed_by 的身份。应把基线放在受控独立位置，保留原始工作簿和摘要。若同时改写两者，单机比对不能提供数字签名级认证。

## 图像生成与审核绑定

实际生成后记录 generation_receipt.tool_call_id、input_asset_ids、input_asset_sha256 映射与 output_sha256。input_asset_sha256 覆盖实际回执所列输入；需要的参考必须真的在其中。实际审图后记录 visual_review.status=passed、具体 evidence 和 reviewed_sha256。已审摘要必须等于生成输出摘要，且与当前图像实际字节一致。

production 及非草稿首尾图编译使用这些绑定。换图、换参考、空文件、失效回执或缺失哈希必须重新核查，不能简单把当前哈希回填到旧批准记录。正常规划草稿仍允许没有真实图片和回执，但不能被称为已审成品。

输出哈希、工具ID和审核人仍是本地记录，不代表已向供应商认证生成来源。真实服务端验证是后续Provider阶段。

## 校验和依赖变化

默认结构检查统一使用随包Schema约束的受支持子集；完整jsonschema选项继续可用。entry与exit必须各恰好一个。三种对白模式在两个编译后端明确表达。损坏或缺失字段先产生结构错误，不再依赖下游KeyError。

图片完整性检查会使用已安装Pillow做实际解码，并限制像素数；这是相对4.1标准库图片编译路径的依赖变化。若需要处理已存在图片而Pillow不可用，明确阻断，不自动安装。仅文本编译及无图片的基本导入校验继续不依赖Pillow。音频/视频目前仅核对非空与摘要，不认证编码或声画质量。

## 安全操作顺序

1. 复制原项目并保存原Excel和原ZIP，不混盖已安装技能。
2. 核对原声字段，建立真实对白分类基线并同步合同映射，不伪造审批。
3. validate contract.json --source source-reviewed.json；需要时再加 --schema。
4. 缺真实素材时只使用 compile 的 --draft。完成真实出图和图审后再作 production 校验。
5. 非草稿编译传入独立 --source；模型提交仍由后续服务适配与独立授权控制。
